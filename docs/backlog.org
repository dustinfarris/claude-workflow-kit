* TODO [#B] session-owned dev server: Claude starts, uses and stops the project's dev server :promote:
:PROPERTIES:
:CREATED:  [2026-10-05 Mon 13:03]
:END:
:LOGBOOK:
- Note taken on [2026-10-05 Mon 13:03] \\
  Follow-up to the 0.8.9 MVP (the "dev server as a session precondition" entry above). Goal: the session, not the human, makes sure the dev server is running, and stops it when no session needs it — for the whole development experience (browser review, logs, staging states), not only so Tidewave answers. Needs its own requirements before any build: what a session may do with a server it controls (start, restart after ~mix.exs~ / ~config/~ / migration changes, read its log), how the session and the human each learn its URL, and what happens to a server the human started by hand.
  Findings from the 2026-10-05 design conversation, so they are not re-derived. (1) ~mix tidewave.proxy~ (tidewave 0.9.1, already in bear-cub) declares only ~@requirements ["loadpaths"]~: it compiles stale deps, never the project, so it adds no project compile at session start; it may briefly wait on Mix's build lock while the server compiles. (2) It is a Mix task from the tidewave dep, so it runs from the project directory and registers in the project's ~.mcp.json~; a user-level entry would spawn a failing server in every other repo. (3) Each proxied tool takes a required ~port~ argument, so the session must be told the port. (4) Claude Code runs a stdio MCP server as a child of the session; when the session ends by any route, including a crash or ~kill -9~, the pipe closes and the proxy exits. That is a reliable end-of-session signal where SessionEnd is not. The candidate shape: ~.mcp.json~ runs a project script instead of the bare proxy; the script starts the server as its own child when the port is free (stdin from ~/dev/null~, output to a log, never to stdout, which is the MCP channel), writes a pidfile and a portfile, runs the proxy in the foreground, and a watcher process stops the server and removes both files once the script is gone; a second session reads the portfile and reuses the server; a server it did not start is never stopped. Rare concurrent sessions in bear-cub make losing the server when the owning session closes acceptable. (5) Port: derived from the repo path (e.g. 4100 + hash mod 900, next free if taken) rather than random, so a restart keeps the port the session and browser already use; a ~mkdir~ lock around check-portfile, pick, start, write closes the two-sessions race. bear-cub's ~config/runtime.exs~ reads ~PORT~ for every non-test env, so a ~PORT~ the script sets wins over ~dev.exs~. (6) One server, not two: a Tidewave-only server beside a human one on 4000 works mechanically (bear-cub's ~listeners: [Phoenix.CodeReloader]~ makes a shared ~_build~ safe) but Tidewave then inspects a VM the human is not looking at — its logs, live state, and PubSub broadcasts (bear-cub's ~:schedule_changed~ scenario staging) stay in the other VM — and both run the asset watchers into one ~priv/static~. (7) A server started by hand has no portfile and would be invisible to the script; either hand starts go through the script, or the script adopts a listening ~beam~ whose cwd is the repo.
:END:
