* 0.8.6 — [2026-10-04]

Two rulings from bear-cub's effort-multiplier batch 1 retro, both about visual work landing in the wrong place.

Visual review is owed before close-out. The batch's stories that touched kiosk visuals deferred every "how does it look" question to the gate, and the gate review then produced three inserted stories — visual defects found at the one point where fixing them means reopening the batch. The retro ruled that a story touching visuals carries its own review. user-stories gains a conditional Definition of Done item, kept as its own verbatim block after the two weight-class blocks: the story's visual changes were viewed at the repo's declared review viewport, in a state staged through its declared staging mechanism, before close-out, with a screenshot at that viewport as the evidence. It is appended only when the story's Design excerpt touches visuals (content from a Screens section of DESIGN.org, or styling) and the repo's CLAUDE.md carries a ~Local review: <viewport> via <staging mechanism>~ line, both halves named. Gated on that line rather than on weight class: the item needs both values to mean anything, so a repo that has not stated how it reviews visuals gets no item and no guessed one, and a repo that has stated it gets the item at either weight class. The line is keyed rather than judged from prose because bear-cub states its convention in a Repo conventions paragraph, and a skill deciding whether arbitrary prose amounts to a declared viewport and staging mechanism is a judgment that can drift; a keyed line is checked by reading it, like ~Verify command:~. Both project-setup CLAUDE.md templates gain the line, optional, directly after ~Verify command:~ and in the same style, with a parenthetical saying the visual review item reads it and that it is omitted when the repo has no local review. The kit hardcodes neither value, and the item's wording points at the line the way the Verify command item points at ~Verify command:~. Story structure item 4 names the new block. The DESIGN EXCERPT SCOPE rules, the AC drift guard, both weight-class Definition of Done blocks, and the STOP boundary are unchanged; story-closeout is unchanged, since its step 4 verifier already audits every DoD item and a screenshot is evidence it can cite. Dry read-through against bear-cub's CLAUDE.md: its Repo conventions name both the viewport (1280 × 800 CSS px) and the staging module (~BearCub.Dev.Scenarios~) in prose but carry no ~Local review:~ line, so under this release its kiosk stories get no item until the line is added there.

Design rounds sit outside open batches. A Claude Design adoption ran inside the same open batch and dominated its time and tokens, and every story it produced had to be inserted rather than planned. Ruling: design iteration happens before user-stories or between batches. README's pipeline section gains one paragraph saying so. No new ceremony and no skill change — user-stories already refuses to open a batch over an open one and requires authorization to insert into it; the paragraph tells the human where the round goes so that path is not the one taken. No hook changes; ~test/hooks_test.sh~ green (86/86).

* 0.8.3 — [2026-09-21]

Tidewave pre-flight at session start. Tidewave's MCP tools only answer while the project's dev server is running, and a session that starts against a stopped one finds out at its first ~mcp__tidewave__*~ call — after the tokens that got it there are spent, and with the recovery landing mid-story rather than before it. The new ~hooks/tidewave-preflight.sh~ is a SessionStart hook that probes the endpoint once with a JSON-RPC ping and, when it is not answering, injects context naming the URL and telling the session to ask the human to start the server before doing dependent work. Advisory by design: it never blocks a tool call and never starts a server, because the enforcing version (a PreToolUse block on ~mcp__tidewave__*~) bites only after the waste has already happened. Applicability is decided by the URL Claude Code itself would dial — ~.mcp.json~ in the project, then the per-project ~mcpServers~ entry in ~~/.claude.json~ — matched on the URL containing ~/tidewave/mcp~ rather than on the server name, since a live registration was found under the name ~jump~. No registered Tidewave means no probe, no network call, and no output, which is what makes it safe in the plugin's own hooks.json alongside prd-lock and post-edit-format rather than in the opt-in path stop-test-gate takes. The probe judges by whether the connection succeeded rather than by the status code alone, so an sse-transport registration answering non-200 while healthy is reported as a transport mismatch instead of a dead server; the 2-second cap means a session start can never hang on it. ~test/hooks_test.sh~ gains 12 hermetic cases over a stub endpoint (~test/fixtures/tidewave-stub.py~) covering silent no-op, refused, live, non-200, and URL discovery from both config files. Green (83/83). Also wired into ~project-setup/copy-in-settings.json~ so the no-plugin fallback keeps parity.

* 0.8.0 — [2026-09-05]

The PRD conversation runs before any brainstorm. In live use the Superpowers brainstorm fired on the first mention of a feature idea, asked a few good questions, and was discussing design before the human had settled what the feature was, whether it was the right feature, or whether it should exist; by the time it stopped it was proposing an implementation plan, and the PRD was extracted after the fact from a design document. Right for a one-shot change to an existing thing; the cart ahead of the horse for a product feature. The 2026-09-01 adversarial review measured the cost of everything downstream of that seam and never named this gap, so it is fixed first, on its own, before any decision about the rest of the kit's shape. Design: ~docs/2026-09-05-prd-conversation-design.org~.

~create-prd~ becomes that conversation. It opens by reflecting the idea back and asking one question; every question passes one test before it is asked — could the answer change the outcomes? — and a question that can only change the mechanism is not asked. Mechanism material that comes up anyway is parked, one line each, in a new scratch file, ~SKETCH.org~, beside PRD.org (template ~templates/SKETCH.org~), and the conversation returns to outcome altitude. The existence question is asked out loud at least once. When the session believes it can state the problem, the success criteria, and the non-goals, it proposes one of four verdicts and the human rules: write the PRD (drafting, the lock, and the human rename are unchanged), set aside (a dated entry in the repo-level ~docs/backlog.org~, the initiative directory removed), different idea (the same entry, then a restart), or bounded with no chain (settled points stated, hand-off to Superpowers). No turn count; a circling conversation says so and asks which unsettled item to take next. The skill never invokes ~superpowers:brainstorming~, never writes DESIGN.org, and keeps its Opus pin. Its closing hand-off names the design brainstorm as the next step, with PRD.org as the fixed contract and SKETCH.org as starting material.

Routing uses the two levers the kit has. Both CLAUDE.md templates gain a Workflow paragraph — a new feature, capability, or initiative goes to create-prd first whether or not the request names it, a session does not invoke brainstorming for such a request, brainstorming is the design conversation and runs once PRD.org exists, and bugs, bounded changes, and refactors go straight to Superpowers — which binds because Superpowers' own priority rule places project instructions above skills; repos without the kit's CLAUDE.md (dotfiles) see no change. The skill description claims the phrasings a feature idea arrives in and says to use it before any brainstorming. Routing cannot be unit-tested: the acceptance test is a fresh bear-cub session opened with a raw feature idea, and if brainstorming still fires first the recorded fallback is to fork the brainstorming skill into the kit with an initiative path ahead of design — rejected for this release as a 4,000-word copy against a moving upstream when the cheaper levers are Superpowers' own declared mechanism.

Conventions and seam: org-conventions names SKETCH.org in the chain location, adds it to the never-cited rule beside the brainstorm spec, says it rides in the PRD lock commit and is edited freely afterward until DESIGN.org exists, gives it a scratch entry in the mutability policy, and gains a Set-aside ideas section naming ~docs/backlog.org~; no crown-jewel block is touched. SKETCH.org living in the initiative directory does not reverse the 2026-07-11 ruling that initiative directories hold only chain documents and brainstorm outputs stay in ~docs/superpowers/specs/~: SKETCH.org is kit-authored by create-prd and committed with the lock, not a brainstorm output, and the human approved its location 2026-09-05. promote-design's input paragraph now says the brainstorm ran against a locked PRD (it no longer "predates the PRD") and that SKETCH.org is not an input, and its reference scrub greps for SKETCH. README's pipeline table starts at the PRD conversation with the design brainstorm second, and the "Brainstorm kickoff fence" section is retired — create-prd now does what the paste-in line asked the human to do by hand; the expected-outcome-prediction paragraph keeps its own heading. PRD.org keeps its name: a rename would touch the lock hook and its tests, three templates, every SC-n citation, both CLAUDE.md templates, the README, and bear-cub's live chains, and mixing it into this behavior change would obscure both; it is a clean follow-up if wanted.

Recorded as follow-up designs, not folded in: the brainstorm-to-DESIGN seam (the review's largest proposed cut; this release's hand-off contract holds under either resolution), the review's four open rulings (PRD lock hook, per-checkbox LOGBOOK notes, the tilde/equals markup convention, weight class), and the close-out cost the bear-cub chore-lifecycle retro exposed (97 close-out and 59 update-design minutes against 44 implementation minutes over five stories). No hook changes; ~test/hooks_test.sh~ green (66/66).

* 0.7.1 — [2026-07-23]

Red-run self-tick guard, retro-born (bear-cub gamification retro, 2026-07-17). Before this release the only integrity language at the verification boundary was phase-close step 1's "never fake a result", scoped to manual PRD gate criteria — nothing anywhere stated what a session does when an automated check stays red and completion pressure invites reading the criterion loosely enough to tick the item anyway. Now stated in all three files that hold a verification boundary, one pass. story-closeout carries the primary rule: a red verify run is never self-ticked — when the check backing an item (the declared ~Verify command:~, a test run, or the check the item itself states) fails and the fix loop cannot make it green, the item is not marked done and its bar is not reinterpreted, narrowed, or substituted to clear the failing result; the failure is surfaced to the human, who may rule a documented deferral, and only that ruling makes =[-]= legitimate for a red-run item, with the ruling recorded in the item's LOGBOOK entry alongside the failing evidence. story-verifier's hard rules gain the matching audit posture: the bar is audited as written, never reinterpreted or weakened to reach a verdict, and a failing run is NOT MET however near the miss. phase-close step 1 extends its existing "never fake a result" sentence (untouched, per the crown-jewel protection on STOP-adjacent gate language) with the same rule for the automated checks: a red run is never recorded as passing by reinterpretation, and a failure unfixable within that step's bounds is surfaced for a human deferral ruling recorded in the gate record, never silently absorbed. The rule applies uniformly at every weight class — it is a prohibition, not ceremony, so there is nothing for personal-mvp to opt out of. Dry read-through against bear-cub's gamification stories confirmed the "check the item itself states" phrasing matches how real AC items are written.
